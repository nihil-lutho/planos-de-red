Programación orientada a componentes

Divide y vencerás: componentes e interfaces

27 de octubre de 2026Lectura: 6 min

Del monolito a las piezas

Antes, un equipo recibía los requerimientos, desaparecía seis meses y entregaba un sistema monolítico: todo en una sola pieza. Cuando algo fallaba, el error afectaba a todo el sistema, y cada cambio pequeño obligaba a mover muchas partes.

La evolución fue así:

  1. Era estructurada: funciones, procedimientos y variables globales.
  2. Orientación a objetos: clases, encapsulamiento y herencia, pero con fuerte dependencia del código fuente.
  3. Componentes: unidades autónomas que se despliegan por separado y se conectan mediante interfaces explícitas.

¿Qué es un componente?

Según Szyperski, un componente es una unidad de composición con interfaces especificadas contractualmente y dependencias de contexto explícitas. Oculta su implementación: quien lo usa solo conoce su contrato, como una caja negra que recibe una entrada y devuelve una salida.

Interfaces provistas y requeridas

  • Provista (piruleta en UML): lo que el componente ofrece a los demás.
  • Requerida (zócalo o media luna): lo que el componente necesita del entorno para funcionar.

El ejemplo de clase en Python

En el primer insumo, el componente de facturación necesita una pasarela de pagos, pero no sabe cuál. Solo conoce el contrato:

class PaymentGatewayInterface(ABC):          # interfaz requerida
    @abstractmethod
    def process_transaction(self, amount, account_id) -> bool: ...

class BillingComponent(BillingServiceInterface):
    def __init__(self, payment_gateway: PaymentGatewayInterface):
        self._payment_gateway = payment_gateway   # dependencia inyectada

# Cableado en tiempo de ejecución
gateway = StripePaymentAdapter()
billing = BillingComponent(payment_gateway=gateway)
billing.create_invoice(user_id="USR-102", amount=150.00)

Si mañana se cambia Stripe por otra pasarela, basta con escribir otro adaptador que cumpla el mismo contrato. El componente de facturación no se modifica.

Ventajas y riesgos

VentajaRiesgo
Mantenimiento: se reemplaza un módulo defectuoso sin tocar el resto.Confianza en código de terceros que no se puede auditar.
Reutilización: pasarelas de pago, generadores de PDF o módulos de autenticación ya hechos.Incompatibilidades cuando el proveedor cambia de versión.
Equipos que trabajan en paralelo sobre contratos definidos.Algo de pérdida de rendimiento por las capas intermedias.

La conclusión conecta con la primera entrada: los componentes funcionan cuando hay una arquitectura que dice cómo deben encajar. Sin ella, volvemos a la Casa Winchester.
